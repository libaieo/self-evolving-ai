# 개발 로드맵 및 단계 정의

이 문서는 모든 대화와 작업에서 단계 번호를 동일한 의미로 사용하기 위한 기준 문서다. 단계 번호는 아래 기준에 따라 고정하며, 범위를 바꿀 때는 이 문서를 먼저 수정한다.

## 단계 1 — 기반 문서와 저장소 구조
**목표:** 프로젝트의 목적, 구조, 개발 규칙을 문서로 고정한다.

**산출물:**
- `README.md`
- `docs/architecture.md`
- `docs/development-roadmap.md`
- `docs/decisions.md`
- `.gitignore`

**완료 조건:** 문서가 저장소에 존재하고 서로 모순되지 않으며, GitHub에서 열람할 수 있다.

## 단계 2 — 최소 실행 기반
**목표:** 실제 실행할 수 있는 최소 프로그램과 테스트 환경을 만든다.

**범위:**
- 사용할 언어와 실행 환경 확정
- 기본 프로젝트 디렉터리 구성
- 환경 설정 예시와 비밀정보 관리 규칙
- 실행 진입점 및 기본 테스트
- 설치·실행 방법 문서화

**완료 조건:** 깨끗한 환경에서 문서대로 실행하고 기본 테스트를 통과할 수 있다.

### 단계 2 진행 기록
- Python 3.11 이상을 기준으로 설정했습니다.
- CLI 진입점과 패키지 메타데이터를 추가했습니다.
- `unittest` 기반 기본 테스트 2개를 추가했습니다.
- GitHub Actions에서 푸시와 PR 시 자동 테스트를 실행하도록 설정했습니다.
- 설치 안내와 `.env.example`을 추가했습니다.
- **검증 기록:** 격리된 로컬 테스트 환경에서 전체 19개 테스트가 통과했습니다. GitHub Actions 및 깨끗한 환경의 패키지 설치 검증은 아직 확인되지 않았으므로 단계 완료 판정은 보류합니다.

## 단계 3 — 요청 해석 및 작업 계획
**목표:** 사용자 입력을 목표, 제약, 위험도, 성공 조건으로 구조화한다.

**완료 조건:** 예시 요청에 대해 일관된 구조의 계획을 만들고 모호한 입력을 식별한다.

### 단계 3 진행 기록
- `RequestAnalysis`와 `TaskPlan` 자료 모델을 추가했습니다.
- 규칙 기반 요청 분석과 결정론적 계획 생성 함수를 추가했습니다.
- `--analyze` 명령행 옵션으로 분석 결과를 JSON으로 출력하도록 했습니다.
- 요청 제약, 긴급도, 위험 키워드, 모호성에 대한 단위 테스트 6개를 추가했습니다.
- 구현 한계와 실행 예시를 `docs/stage-3-request-planning.md`에 기록했습니다.
- **검증 기록:** 격리된 로컬 테스트 환경에서 요청 분석 테스트가 통과했습니다. GitHub Actions 결과 확인은 남아 있습니다.

## 단계 4 — 전문 모듈 실행 체계
**목표:** 작업 유형별 모듈을 등록하고 적절한 모듈을 선택·실행한다.

**완료 조건:** 최소 두 종류의 모듈을 인터페이스에 따라 실행하고 실패를 처리한다.

### 단계 4 진행 기록
- 공통 모듈 계약(SpecialistModule)과 결과 모델(ModuleResult)을 추가했습니다.
- 요약 모듈과 체크리스트 모듈을 등록하고 별칭으로 선택할 수 있게 했습니다.
- 디스패처가 미등록 작업과 모듈 예외를 표준 오류 결과로 변환하도록 했습니다.
- CLI에 --list-modules, --run, --request 옵션을 추가했습니다.
- 자동 테스트를 추가했으며 격리된 로컬 테스트 환경에서 관련 테스트가 통과했습니다. GitHub Actions 결과 확인은 남아 있습니다.

## 단계 5 — 검증 및 자기교정
**목표:** 결과를 검증하고 오류를 수정한 뒤 재검증한다.

**완료 조건:** 실패 사례를 테스트로 재현하고 수정 전후 결과를 기록한다.

## 단계 6 — 로그, 감사 및 경보
**목표:** 주요 실행, 오류, 수정, 승인 내역을 추적한다.

**완료 조건:** 로그에서 실행 흐름을 확인할 수 있고, 정해진 오류 조건에 경보가 발생한다.

## 단계 7 — 기억 활용
**목표:** 승인된 지식을 저장·검색·재사용한다.

**완료 조건:** 저장 기록에 출처와 날짜가 포함되고, 검색 결과의 적용 가능성을 평가한다.

## 단계 8 — 지식 환류
**목표:** 과거 작업에서 반복 가능한 개선점을 추출하고 평가한다.

**완료 조건:** 환류 제안이 근거·영향 범위·위험을 포함하며, 승인 없이 핵심 규칙을 변경하지 않는다.

## 단계 9 — 법·윤리 변화 감지 및 사용자 개입
**목표:** 관련 규정과 안전 요구사항의 변화를 검토 대상으로 표시하고, 필요한 작업에 사용자 승인을 적용한다.

**완료 조건:** 변경 제안의 출처·날짜·영향을 기록하고 승인 전후 상태를 구분한다.

## 단계 10 — 통합 시험 및 안정화
**목표:** 전체 모듈을 연결하고 통합·회귀·오류 복구 테스트를 수행한다.

**완료 조건:** 주요 시나리오 테스트가 통과하고 알려진 한계와 복구 방법이 문서화된다.

## 테스트 및 디버깅 기록
- 전체 테스트 19개 통과(격리된 임시 환경에서 저장소 소스·테스트 내용을 바탕으로 실행).
- CLI 기본 출력과 테스트 기대값 불일치를 수정했습니다.
- CLI 테스트가 unittest 인자를 읽지 않도록 테스트의 `sys.argv`를 격리했습니다.
- 영어 단어 내부의 `it` 문자열이 모호성으로 오탐되는 문제를 수정하고 회귀 테스트를 추가했습니다.
- 상세 내용: [테스트 및 디버깅 보고서](test-and-debug-report.md).
- GitHub Actions와 깨끗한 환경의 패키지 설치 검증은 별도 확인 전까지 미확인입니다.

## 공통 개발 규칙
1. 한 단계의 완료 조건을 확인한 뒤 다음 단계로 이동한다.
2. 기능을 구현하기 전에 입력, 출력, 실패 조건을 정의한다.
3. 테스트하지 않은 기능은 완료로 표시하지 않는다.
4. 실제 실행 결과와 문서상 계획을 구분한다.
5. 단계 범위가 바뀌면 `docs/decisions.md`에 이유를 기록한다.
6. API 키와 비밀번호는 코드나 Git 기록에 저장하지 않는다.
7. 중요한 외부 변경은 사용자의 명시적 승인을 받는다.

## 현재 상태
- 단계 1: 완료 — README, 아키텍처, 개발 로드맵, 설계 결정 기록, `.gitignore`를 생성하고 GitHub에서 내용을 확인했습니다.
- 단계 2: 구현 중 — 기본 코드와 테스트 자동화 파일을 추가했습니다. 로컬 테스트는 통과했지만 설치 및 GitHub Actions 결과 확인이 남았습니다.
- 단계 3: 구현 중 — 요청 분석과 계획 생성 기능 및 단위 테스트를 추가했고 로컬 테스트는 통과했습니다. GitHub Actions 결과 확인이 남았습니다.
- 단계 4: 구현 중 — 전문 모듈 인터페이스, 모듈 레지스트리, 디스패처, 예시 모듈 2개와 테스트를 추가했으며, 자동 테스트 결과 확인이 남았습니다.
